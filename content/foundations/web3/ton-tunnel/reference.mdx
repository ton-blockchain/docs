This reference describes ADNL Tunnel v0.2.2. Client integrations may embed another library version, as listed below.

## Client configuration and node pools

| Field                 | Purpose                                                                     |
| --------------------- | --------------------------------------------------------------------------- |
| `NodesPoolConfigPath` | Path to the public pool JSON file                                           |
| `TunnelSectionsNum`   | Number of sections used to construct a route; generated default `1`         |
| `PaymentsEnabled`     | With `false`, only entries whose `Payment` is absent or `null` are eligible |
| `TunnelServerKey`     | Client's generated private tunnel key                                       |
| `Payments`            | Client payment configuration, including private keys                        |

A [pool](/foundations/web3/ton-tunnel/use#configure-the-pool) contains a `NodesPool` array. Each entry has a `Key` and an optional `Payment` object. `Key` is an Ed25519 public key encoded as base64 in JSON. `Payment` contains a payment-node chain and packet prices. Export this file with `-gen-shared-config` rather than copying a private configuration.

The pool must contain enough eligible entries for `TunnelSectionsNum`. Outgoing and returning routes can use different intermediate nodes.

## Client integrations

| Application                   | Embedded ADNL Tunnel | Configuration object | Activation                               |
| ----------------------------- | -------------------- | -------------------- | ---------------------------------------- |
| Tonutils-Proxy v1.8.3         | v0.1.8               | `TunnelConfig`       | Nonempty `NodesPoolConfigPath`           |
| tonutils-reverse-proxy v0.6.0 | v0.2.1               | `tunnel_config`      | `--enable-tunnel` with a configured pool |

These are application integration points, not flags of `tunnel-node`. Keep each application's generated configuration and private keys when changing tunnel settings.

## Relay CLI

| Option                           | Default                                   | Purpose                                                             |
| -------------------------------- | ----------------------------------------- | ------------------------------------------------------------------- |
| `-config <FILE>`                 | `config.json`                             | Private relay configuration; generated if absent                    |
| `-gen-shared-config <FILE>`      | Disabled                                  | Export a public node pool and exit; output path must end in `.json` |
| `-payment-node <KEY_HEX>`        | Automatic selection or interactive prompt | Select a payment peer by its 32-byte public key in hexadecimal      |
| `-v <LEVEL>`                     | `2`                                       | Logging verbosity                                                   |
| `-log-filename <FILE>`           | `tunnel.log`                              | Log file path                                                       |
| `-log-disable-file`              | `false`                                   | Disable file logging                                                |
| `-metrics-listen-addr <ADDRESS>` | Disabled                                  | HTTP address for Prometheus metrics                                 |

## Relay configuration

| Field              | Purpose                                                          |
| ------------------ | ---------------------------------------------------------------- |
| `TunnelServerKey`  | Private Ed25519 seed identifying the relay; keep it secret       |
| `TunnelListenAddr` | UDP listener, default `0.0.0.0:17330`                            |
| `ExternalIP`       | Public IPv4 address advertised for the relay                     |
| `NetworkConfigUrl` | TON network configuration URL; mainnet by default                |
| `TunnelThreads`    | Listener worker count; `0` uses the CPU count                    |
| `PaymentsEnabled`  | Whether to initialize the payment service; default `false`       |
| `Payments`         | Payment keys, database path, channel settings, and packet prices |

## Network endpoints

The fixed UDP listener accepts tunnel traffic. When acting as an outbound gateway, the relay also allocates a UDP socket on an operating-system-selected port. Return traffic uses this socket. Network rules must accommodate these gateway sockets as well as the configured listener.

`ExternalIP` does not configure port forwarding or a firewall.

## Payment settings

| Field under `Payments`   | Purpose                                                         |
| ------------------------ | --------------------------------------------------------------- |
| `MinPricePerPacketRoute` | Minimum price in nanograms per routed packet                    |
| `MinPricePerPacketInOut` | Minimum price in nanograms per gateway inbound/outbound packet  |
| `PaymentsNodeKey`        | Private seed for the Payment Network node                       |
| `ADNLServerKey`          | Private seed for the payment transport                          |
| `WalletPrivateKey`       | Private seed for the payment wallet                             |
| `DBPath`                 | Persistent payment database, generated default `./payments-db/` |
| `ChannelsConfig`         | Payment Network channel policy                                  |

The shared configuration advertises payment terms when `PaymentsEnabled` is true and at least one price is positive. Private seeds are not included in the export.

Without `-payment-node`, startup selects an active channel using the peer's Gram deposit, or prompts for a peer if none is available. The CLI option accepts hexadecimal; the prompt accepts base64. Both identify a 32-byte payment-node public key, distinct from the relay key and wallet address.

### Payment routes

Each paid pool entry contains a `Payment.Chain` array, ordered from the client's first payment peer to the relay's payment node. The client prepares a payment channel with the first peer. Intermediaries need outgoing channel capacity to the next payment peer.

The relay's pool export starts with a single entry for its own payment-node key. Selecting a peer with `-payment-node` does not add that peer to the exported chain. For an indirect payment route, the pool must include the intermediary keys and their agreed terms.

For native Gram payments, the fields under each `Payment.Chain` entry are:

| Field                          | Meaning                                                        |
| ------------------------------ | -------------------------------------------------------------- |
| `NodeKey`                      | A 32-byte payment-node public key encoded as base64.           |
| `MinFeePerVirtualChannel`      | Minimum fee per virtual channel, as a decimal string in GRAM.  |
| `PercentFeePerVirtualChannel`  | Percentage fee applied when building the payment route.        |
| `MaxCapacityPerVirtualChannel` | Maximum virtual-channel capacity, as a decimal string in GRAM. |

`Payment.PricePerPacketRouteNano` and `Payment.PricePerPacketOutNano` specify the route and gateway prices in nanograms per packet. These packet prices are separate from virtual-channel fees.

### Client funding

A paid client runs an embedded Payment Network node with its own wallet and database, configured under `Payments`. Its startup log prints the wallet address to fund. The client wallet, the relay wallet, and payment-channel capacity are separate balances.

The generated v0.2.2 client configuration enables automatic balance management under `Payments.ChannelsConfig.SupportedCoins.Ton.BalanceControl`:

| Field                       | Generated value, GRAM | Meaning                                               |
| --------------------------- | --------------------: | ----------------------------------------------------- |
| `DepositWhenAmountLessThan` |                   `1` | Threshold for requesting an automatic channel top-up. |
| `DepositUpToAmount`         |                   `3` | Target channel balance after the top-up.              |

Review these settings before funding the client wallet. Wallet funds must also cover deployment and transaction fees. The target applies to each channel, not to total spending. These defaults are client policy, not a fixed cost for using a tunnel.

## Console commands

Enter these commands in the running relay's console, not in a shell.

| Command               | Result                                                                                   |
| --------------------- | ---------------------------------------------------------------------------------------- |
| `stats`               | Cumulative packet and prepaid-credit counters per active section                         |
| `speed`               | Toggle per-second packet statistics                                                      |
| `balance`             | Summed available local Gram balance across active payment channels                       |
| `capacity`            | Summed available peer-side Gram balance across active payment channels                   |
| `wallet-ton-balance`  | Balance of the separate payment wallet                                                   |
| `wallet-ton-transfer` | Interactive transfer from the payment wallet; prompts for recipient, amount, and comment |

Payment commands require paid mode. Channel balances and capacity are separate from the wallet's on-chain balance.
