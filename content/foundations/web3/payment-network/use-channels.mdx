Initialize and fund a channel, send payments, then withdraw funds or close the channel using the standalone v1.3.2 node.

## Prerequisites

- A running [payment node v1.3.2](/foundations/web3/payment-network/run-node) configured for mainnet and manual balance management, with its original private keys and database
- A reachable mainnet peer and its payment-node public key in base64
- Funds in the node's wallet for the chosen asset and native-currency transaction fees

<Callout
  type="caution"
  title="Funds and channel state"
>
  Funding, withdrawals, and closure can send on-chain transactions. Mainnet transfers cannot be rolled back. Check the peer, destination, asset, amount, and fees before submitting the final console response. Preserve the private keys and payment database, and keep the node running during settlement.
</Callout>

## Initialize the channel

Enter [`init`](/foundations/web3/payment-network/reference#channel-console-commands) inside the node's console:

```text
init
```

When prompted, enter the peer's base64 payment-node public key. This is not the peer's wallet address or ADNL transport key.

Wait for “channel opened offchain”, then run [`list`](/foundations/web3/payment-network/reference#channel-console-commands) to find the local channel address. In this version, initialization exchanges signed configuration off-chain. It does not by itself prove that the channel contracts are deployed or funded.

## Fund the local side

Enter [`topup`](/foundations/web3/payment-network/reference#channel-console-commands):

```text
topup
```

Answer the prompts in order:

1. The local channel address from `list`.
1. The configured currency symbol, such as `TON` for the native currency.
1. The amount in whole-coin units, for example `1` rather than `1000000000` for one native coin.

The first top-up can deploy and activate the channel contracts. Wait for “topup transaction completed”, then allow the node to process the on-chain update.

For jettons or extra-currencies, enable the asset's configuration on the participating nodes first. [Symbols and decimals](/foundations/web3/payment-network/reference#assets-and-amounts) come from that configuration.

## Verify channel capacity

Enter [`show`](/foundations/web3/payment-network/reference#channel-console-commands), then the local channel address. Check the peer identity, on-chain activation flags, and balances for the chosen asset.

The local available outgoing balance is separate from incoming capacity. To receive payments through the peer, its side must provide sufficient capacity. Funding the local node's wallet does not fund the peer's side.

## Send a payment

Before sending, obtain the ordered base64 payment-node keys ending with the recipient, agree on forwarding fees, and check capacity for the selected asset along the route. Record the relevant channel balances on the sender and recipient nodes.

In the sender's node console, enter [`send`](/foundations/web3/payment-network/reference#virtual-channel-commands):

```text
send
```

Answer the prompts in order:

1. The next nodes in the route, including the recipient, separated by commas without spaces. Do not include the sender's node key.
1. The configured currency symbol, such as `TON`.
1. The amount the recipient should receive, in whole-coin units.
1. The forwarding fee per intermediate node, in the same asset's units.

For a direct payment, the route contains only the recipient's key. For a routed payment, consecutive nodes must have suitable channels and capacity.

The command reports “virtual transfer requested”. This confirms submission, not completion at the recipient.

### Verify receipt

On both sender and recipient nodes, use `show` followed by the relevant local channel address. Compare the selected asset's available balances before and after the payment has settled off-chain. Account for fees, locked capacity, and any concurrent channel activity.

Do not treat a request log or the sender's wallet balance as proof of receipt. The recipient should confirm the resulting channel state.

### Send repeated payments

<span
  id="repeated-payments"
/>

For a reusable virtual channel, [`open`](/foundations/web3/payment-network/reference#virtual-channel-commands) follows the same route and capacity prompts but returns a private signing key. The sender uses [`sign`](/foundations/web3/payment-network/reference#virtual-channel-commands) to produce a signed payment state. The recipient uses [`close`](/foundations/web3/payment-network/reference#virtual-channel-commands) with that state to settle it. Keep the private signing key with the sender, not the recipient.

## Withdraw part of the balance

Use a mainnet destination address and check the available balance before withdrawing.

In the node's console, enter [`withdraw`](/foundations/web3/payment-network/reference#channel-console-commands):

```text
withdraw
```

Provide the local channel address, destination wallet address, currency symbol, and amount in whole-coin units when prompted.

The command requests a withdrawal through the channel. Verify the resulting transaction and destination balance; a submitted request is not a completed withdrawal. Withdrawing funds reduces capacity available for subsequent payments.

## Close the channel

Check pending obligations before requesting closure. Keep the node running and its state available during settlement.

### Close cooperatively

Check the [cooperative-closure conditions](/foundations/web3/payment-network/reference#closure-settings), then enter:

```text
destroy
```

Provide the local channel address. The node reports “cooperative channel closure attempt has been started”.

Wait for completion and verify the on-chain results. An accepted request also schedules the [non-cooperative fallback](/foundations/web3/payment-network/reference#closure-settings).

### Close without cooperation

To request non-cooperative closure directly, inspect the channel state and active obligations, then enter:

```text
kill
```

Provide the local channel address. The node reports “uncooperative channel closure has been started”.

This begins a settlement process governed by the channel's [quarantine, conditional-settlement, and action deadlines](/foundations/web3/payment-network/reference#closure-settings). Funds are not necessarily available immediately. Preserve the latest signed state and keep the node online to process the required steps.

### Verify closure

Use `list_all` to include closing and inactive channels, then `show` with the local address. Check the final state and resulting on-chain transfers. A channel disappearing from `list`, which shows active channels only, is not sufficient proof that settlement finished.

## Troubleshoot

| Problem                                   | Check                                                                        |
| ----------------------------------------- | ---------------------------------------------------------------------------- |
| Invalid key format or length              | Use the peer's 32-byte payment-node public key encoded as base64.            |
| Unknown currency                          | Check the enabled asset and symbol on each participating node.               |
| Insufficient wallet funds                 | Check both the asset balance and native currency for transaction fees.       |
| Channel listed but not active on-chain    | Inspect the activation flags and the result of the first top-up.             |
| Route cannot be opened                    | Check every peer key, channel, deadline policy, fee, and available capacity. |
| Request submitted but receipt unconfirmed | Inspect both endpoints' channel states and logs before retrying.             |
| Withdrawal cannot proceed                 | Check available balance, fees, peer connectivity, and pending obligations.   |
| Cooperative close remains pending         | Check the peer's response and the scheduled fallback in the node logs.       |
| Forced closure is not finished            | Check the contract deadlines and the node's settlement progress.             |
